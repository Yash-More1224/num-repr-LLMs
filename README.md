# Number Representations in Language Models: Arithmetic vs. Faithful Number Copying

Language models usually see numbers as ordinary BPE subword pieces (`"1874"` might become `["18", "74"]`), so the model has no direct sense of a number's value. Several papers propose alternative number representations. This project asks a practical question:

> **Which number representation lets one model do both: compute arithmetic correctly *and* copy numbers faithfully when generating text?**

Four representations are implemented on the same GPT-2 (small) backbone, trained from scratch, and evaluated on two complementary tasks:

| Task | What it tests | Data |
| --- | --- | --- |
| **ToTTo** (table-to-text) | Copying numbers from a table into a fluent sentence without hallucinating | ~120K train examples; 200 dev examples for evaluation (179 contain numbers) |
| **Arithmetic** | Computing a numeric answer | 5,000 BIG-bench-style questions (`"What is 87 plus 684?"`) generated by `data/download_bigbench.py`: +, -, x, / ; split 4000 / 500 / 500 |

## Representations compared

| Model | How numbers are represented | How numbers are generated |
| --- | --- | --- |
| **BPE** (baseline) | Standard subword tokens, no special handling | Token by token |
| **Digit** | Every digit is its own token (`1874` -> `1 8 7 4`) | Digit by digit |
| **xVal** ([Golkar et al., 2023](https://arxiv.org/abs/2310.02989)) | Number replaced by a `[NUM]` token whose embedding is scaled by the value (multi-scale, `tanh`-bounded) | Scalar regression head (MSE loss) |
| **FoNE** ([Zhou et al., 2025](https://arxiv.org/abs/2502.09741)) | Number replaced by a `[NUM]` token plus Fourier features `sin/cos(2*pi*x/10^i)` that encode each digit | All digits decoded in parallel by digit-wise classification |
| **FoNE-DP** (my variant) | Same as FoNE | Adds a small bottleneck projection head (768 -> 64 -> 768) at `[NUM]` positions, to test whether it reduces conflict between the language loss and the number loss |

## Results

### ToTTo: copying numbers into text (n = 200)

| Model | BLEU | Number Exact Match | Hallucination Rate (lower is better) |
| --- | --- | --- | --- |
| BPE | **33.41** | **90.6%** | **10.6%** |
| Digit | 25.88 | 72.5% | 26.3% |
| xVal | 22.27 | 6.7% | 83.8% |
| FoNE | 31.29 | 83.9% | 17.8% |
| FoNE-DP | 31.88 | 82.3% | 17.5% |

### Arithmetic (n = 500)

| Model | Exact Accuracy | Within 1% |
| --- | --- | --- |
| BPE | 2.0% | 5.6% |
| Digit | 10.0% | 17.2% |
| xVal | 0.0% | 11.6% |
| FoNE | **44.6%** | **51.6%** |

### Takeaways

- **FoNE gives the best balance.** It is about 4.5x more accurate than any other method on arithmetic, while staying close to BPE on text fluency (31.3 vs 33.4 BLEU) and number copying (83.9% vs 90.6%).
- **BPE is the best pure copier but cannot compute.** It treats `1874` like the word `"London"`: easy to copy, but with no notion of value.
- **Digit tokenization is a middle ground.** Producing a number takes several correct predictions in a row, so one wrong digit ruins the whole number.
- **xVal struggles with exact values.** A single continuous scalar rarely lands on the exact integer, which hurts both tasks.
- **FoNE-DP performs the same as FoNE.** The extra projection head is not needed: the FoNE backbone already handles both losses at this small scale. This agrees with the conclusion of the FoNE paper.

### Notable implementation fixes

- **FoNE / xVal decoding:** during generation, a newly produced `[NUM]` token was fed back into the model with value `0` and no number mask. Because the model never saw that during training, it fell into loops of repeated numbers. Feeding the predicted value back in raised FoNE's ToTTo BLEU from 18.4 to 31.3 and cut its hallucination rate from 53.5% to 17.8%.
- **Digit decoding:** the tokenizer's decoder attached punctuation to the last digit (`"4."`), which broke rejoining digits into numbers. Fixing it raised Digit's Number Exact Match from 23.6% to 72.5%.
- **xVal:** re-implemented the paper's multi-scale `tanh` embedding, replacing a naive linear scaling that made activations blow up for large numbers.

## Usage

All commands are run from the repository root. Training used 4x RTX 2080 Ti with `torchrun`; set `--nproc_per_node=1` for a single GPU.

```bash
pip install -r requirements.txt
```

### ToTTo

Download ToTTo from [google-research-datasets/ToTTo](https://github.com/google-research-datasets/ToTTo) into `totto_data/`.

```bash
# 1. Preprocess and train tokenizers
python data/preprocess.py --data_dir totto_data --output_dir processed
python tokenizer/train_tokenizer.py --corpus processed/tokenizer_corpus.txt --output_dir tokenizer/totto_bpe --vocab_size 16000
python tokenizer/train_digit_tokenizer.py

# 2. Train (swap train_fone.py for train_bpe / train_digit / train_xval / train_fone_dp)
PYTHONPATH=. torchrun --nproc_per_node=4 train/train_fone.py \
    --config configs/train_config.yaml --model_config configs/model_config.yaml

# 3. Evaluate
PYTHONPATH=. python eval/eval_fone.py \
    --checkpoint checkpoints/fone/fone_best_epoch*.pt \
    --config configs/model_config.yaml --train_config configs/train_config.yaml \
    --output results/totto/fone.json
```

### Arithmetic

```bash
python data/download_bigbench.py --output_dir data/bigbench_arithmetic --n_examples 5000

# model_type: bpe | digit | xval | fone
PYTHONPATH=. torchrun --nproc_per_node=4 train/train_bigbench.py --model_type fone \
    --config configs/bigbench_train_config.yaml --model_config configs/model_config.yaml

PYTHONPATH=. python eval/eval_bigbench.py --model_type fone \
    --checkpoint checkpoints/fone_bigbench/fone_bigbench_best_*.pt \
    --config configs/model_config.yaml --train_config configs/bigbench_train_config.yaml \
    --test_data data/bigbench_arithmetic/test.jsonl --output results/bigbench/fone.json
```

### Browse outputs

```bash
pip install streamlit
streamlit run app.py
```

## Metrics

- **BLEU:** n-gram overlap between the generated sentence and the reference.
- **Number Exact Match:** share of reference numbers reproduced exactly in the output.
- **Hallucination Rate:** share of generated numbers that do not appear in the reference.
- **Exact Accuracy / Within 1%:** the arithmetic answer is exactly right, or within 1% relative error.
